# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## Unreleased (v0.3.0)

A ground-up overhaul of the feature taxonomy and of the schema that expresses it.
No group or feature path from 0.2.0 survives unchanged: the taxonomy is now a single recursive tree of 18 top-level categories, named for the question each answers rather than for the technology it describes.
Resolves #19, #28, #29, #30, #32, #35, #39, #65-#103 (as applicable), #108-#114, and #122-#129.
The question of whether 18 top-level categories is still too many remains open, and is tracked separately.

### Changed

#### Schema and tooling

- **Features nest to arbitrary depth.** A taxonomy node is either a **leaf** (`key: "description"`) or a **branch** (`description` plus a `members` mapping of further nodes), and branches and leaves can be siblings. This replaces the fixed group → member layering, in which every capability had to be flattened into a two-level name.
- **`value` and `source` live on leaves only.** A leaf's `value` is a plain scalar and its `source` a plain list of URLs. Capabilities that differ between investment and operation are sibling leaves rather than a qualified single value: `cost.functional_form.fixed_charge` is a branch with an `investment` branch and an `operation` leaf. Where one source evidences several sibling leaves, the URL is repeated on each.
- **No `__` in taxonomy names.** Namespaces are expressed as real nesting (`asset__cost__investment.unit` → `cost.functional_form.fixed_charge.investment`, `transmission__opf` → `network.power_flow.optimal_power_flow`, `time__resolution__simplification` → `tractability.dimension_reduction.temporal`). Cross-references inside descriptions use a single dotted path throughout.
- The generator validates the taxonomy directly: branches must declare exactly `description` and `members` with at least two members; member names must be valid identifiers that avoid `__` and the reserved names `source` / `value` / `description` / `members`; and two paths may not generate the same model name.
- Feature values default to the explicit `?` (unknown) rather than a bare `null`, so an unanswered feature is visibly unanswered in a list a maintainer is part-way through filling.
- Generated tool/use-case templates are written in taxonomy order rather than alphabetical order, so the file a maintainer edits reads in the same order as the file they read for reference.
- Generated JSON schemas are roughly half the size they would otherwise be, by using `Field(default_factory=...)` in place of `Field(default=...)` so Pydantic does not inline a fully-materialised default subtree into every `$def`.
- Feature descriptions no longer use "a.k.a."; alternative names will be carried by a separate `also_known_as` option.
- CONTRIBUTING.md documents the nested schema and recommends per-sub-leaf source comments when citing a feature that splits into several sub-leaves.

#### Taxonomy

- **`processes`** replaces `asset__candidates`: fundamental carrier-flow capabilities defined by mathematical role (`boundary_exchange`, `conversion`, temporal / spatial / delayed / buffered / discrete / state-changing transfer, `explicit_demand`) rather than by named asset types. `conversion` splits by flow topology into `one_to_one`, `multi_carrier_io` (several carriers per process at fixed ratios, e.g. back-pressure CHP), and `flexible_ratio` (optimiser-chosen flow ratios, e.g. extraction-condensing CHP, heat pumps serving heat and cooling). `explicit_demand` splits into `inelastic`, `price_responsive`, and `mobile_storage` (EV fleets / V2G: demand with embedded storage whose grid attachment follows a travel pattern). `system__carriers` is gone: multi-carrier coupling is a property of `conversion`, not a separate feature.
- **`network`** consolidates `transmission__opf`, `transmission__limits`, `transmission__network` and the `power_flow__*` groups into `network.power_flow` (`optimal_power_flow`, `sensitivity_limits`, `network_limits`, `network_devices`, `unbalanced_flows`) alongside a new `network.hydraulic_flow` (`linearised_flow`, `composition_tracking`). `ptdf` is redefined as the input-side flow-based power-flow formulation.
- **The top level recovers the decomposition of an optimisation problem.** `decisions` (what can be decided, and of what mathematical type), `constraints` (what bounds the feasible region), `cost` (what enters the objective as a term) and `objective` (what shape the objective itself takes) now sit alongside each other, with `math` covering access to and extension of the formulation those four describe. `asset` is gone as a group: it had been left holding only the mathematical representation of asset decisions once `processes` took what an asset *does* and `constraints` took what limits it, so nothing in it was actually about assets as objects.
  - **`asset` → `decisions`**, with `capacity_representation` → `investment` and `operating_representation` → `operation`, adopting the `investment` / `operation` axis used throughout the rest of the taxonomy. Descriptions now carry the "representation" sense the old member names held: these say how a decision is *represented*, not what bounds it or what it costs. `multi_period` is reworded from "capacities can be defined across multiple investment periods" to the capacity decision being *indexed over* investment periods, which is a variable-shape claim rather than a horizon one. No members were added or removed; nothing elsewhere in the taxonomy was a better fit to join them, which is why the group is small rather than accidentally thin.
- **`asset.cost` → top-level `cost`, restructured to mirror `constraints`.** Its old parent described "the individual assets that make up the system", which `annuitisation` (financing conventions) and `threshold_deviation` (feed-in tariffs, redispatch settlement) already contradicted, as does any cost charged once for a group of assets at a site. Promoted, it takes the same three facets as `constraints`: `temporal_scope` (`sequential` ← `inter_temporal`, `cumulative`), `breadth` (`assets`, `spatial`, `combined`) and `functional_form` (`fixed_charge` ← `unit`, `nonlinear`, `threshold_deviation`), with `annuitisation` remaining a plain sibling as it has no `constraints` analogue.
  - **`cost.temporal_scope` deliberately has no `pointwise` member**, and the asymmetry against `constraints.temporal_scope` is informative rather than an oversight. `unit` looks like the pointwise case but its defining feature is that cost does *not* scale with magnitude — a statement about form, not time — so it becomes `functional_form.fixed_charge`, alongside `nonlinear` (varies non-linearly) and `threshold_deviation` (varies with deviation from a reference); a fixed charge steps at zero and needs a binary or integer decision to attach to. The genuinely pointwise cost, accruing within a period in proportion to the decision it attaches to, is the declared baseline and is not tracked; a cost coefficient that merely varies by timestep is `model_definition.configurable_dimensions`. There is likewise no `boundary_conditions` member, as costs have no analogue of it.
  - **`cost.breadth` is not a restatement of `constraints.breadth`.** In PyPSA every cost is a per-component attribute (`capital_cost` / `marginal_cost` on generators, links, lines, stores, storage_units, transformers) while cross-asset *limits* have a dedicated `GlobalConstraint` mechanism — so a tool can hold limits across a fleet while still requiring every cost to be entered per asset. The two are independently evidenced capabilities. `cost.breadth` takes the same axis-completeness exemption as `constraints.breadth`, and for the same reasons.
  - **The misfiled learning curve is corrected.** `inter_temporal` was defined as costs on a *change* in a variable between periods — sequential — but its only investment example was a learning rate penalty, which is cost varying with *accumulated* deployment. Learning moves to `cost.temporal_scope.cumulative.investment`, paired with `constraints.temporal_scope.cumulative.investment.path_dependent` as the limit-side expression of the same effect; `cost.temporal_scope.cumulative.operation` is its operating counterpart. `sequential.investment` keeps the genuine change-between-periods case, a retirement / decommissioning charge (`Generator.RetirementCost` in PLEXOS).
- **`math.soft_constraints` → `constraints.soft_constraints`.** Relaxing a constraint is a constraint capability; it sat in `math` only because that is where generic mechanisms accumulated. It is a top-level member of `constraints` rather than a `functional_form` one, since `functional_form` is specifically about the problem class handed to the solver and hard-versus-soft is not a problem-class statement. It now names all three legs of its relationship: the generic mechanism (here), the built-in economic version (`cost.functional_form.threshold_deviation`), and the reliability-specific case (`constraints.reliability.unserved_demand`). `math.piecewise_formulation` stays put but now states the contrast that justifies it — the tool offering constructs for a user to build with, against `tractability.reformulation.nonlinear_handling.function_conversion` doing the conversion automatically.
- **`constraints`** is the single home for "how can the problem be constrained?". `temporal_scope` names most of the limits themselves, grouped by what each binds in time (`pointwise`, `sequential`, `cumulative`, `boundary_conditions`); `reliability` (`operating_reserve`, `probabilistic_reliability_limit`, `unserved_demand`, `contingency_constrained`) and `dedicated_flow_routing` name further limits whose defining feature is the quantity held rather than its form in time; `breadth` (`assets`, `spatial`, `combined`) records how far a single limit reaches across the model's other dimensions; and `functional_form` (`linear_multi_variable`, `quadratic`, `nonlinear`) records the mathematical relationship a limit expresses. It absorbs `asset__operating_constraints`, `asset__operating_characteristics` (functional form is a property of the constraints a tool can build, not of an asset), `asset__chaining`, `system__limits`, and the deterministic half of `robustness`.
  - **Limits are cut by temporal form, with reach recorded separately.** The members previously mixed two unlike questions: three of them (`intra_temporal`, `inter_temporal`, `total`) classified what a limit binds in time, while `inter_asset` and `inter_spatial` classified how far it reaches. Presented as siblings these read as alternatives, so a limit that did both — a carbon budget accumulated over time *and* summed across a fleet — had no single correct home, and `total` needed the phrase "an asset's" to disambiguate, contradicting its own cross-asset `investment` members. Reach is not a mathematical form: a limit on one asset and the same limit on a fleet differ only in index set. So the temporal question keeps the tree — `intra_temporal` → `temporal_scope.pointwise` (binds each period independently), `inter_temporal` → `temporal_scope.sequential` (binds a difference between periods, or distinct periods to one another), `total` → `temporal_scope.cumulative` (binds a total accumulated over a window, not its distribution) — and reach becomes `constraints.breadth`: `inter_asset.{investment,operation}` → `breadth.assets.{investment,operation}`, `inter_spatial.{investment,operation}` → `breadth.spatial.{investment,operation}`. A system-wide annual CO2 cap is now recorded as `temporal_scope.cumulative.operation.impact_budget` plus `breadth.combined.operation` — two entries answering two different questions, rather than one contested classification. `commitment` dissolves into `pointwise`, a must-run or forced-outage flag binding one timestep at a time; its `investment` leaf becomes `pointwise.investment.unit_purchase`.
  - **`breadth` is a peer of `temporal_scope`, not a member of it, and is named for the dimensions it spans.** Nesting reach inside `scope` left `scope` doing two jobs and so stopped it being a partition; promoting it makes the asymmetry explicit — time is an organising axis because a pointwise capacity bound and a cumulative capacity target are *different* features, whereas a fleet-wide and a per-asset CO2 cap are the *same* feature at different reach. `multi_asset` / `multi_region` → `assets` / `spatial`, matching the dimension vocabulary already used by `tractability.dimension_reduction` and `tractability.variable_fidelity.resolution`. One gap is filled: `combined`, for a single limit spanning several assets *and* several spatial units at once — a real discriminator, since a tool can support per-region fleet limits without supporting a global one. There is deliberately no `scenarios` member: a limit indexed across scenario members is what every scenario method in `uncertainty` already implies, so recording it separately would double-count rather than discriminate. `constraints.breadth` is exempted from the axis-completeness test: it omits `temporal` because time carries its own structure in `temporal_scope`, omits `scenarios` for the reason just given, and adds `combined`, which is not a dimension.
  - **`path_dependent` moves into `temporal_scope.cumulative` as a leaf under each of `investment` and `operation`.** As a top-level member it described a mechanism rather than a limit; read as a limit whose *bound* is determined by accumulated history rather than by an input parameter, it is a cumulative constraint like any other (a learning curve raising deployable capacity in later periods; degradation or fouling lowering available capacity or efficiency). `cumulative` is widened accordingly. The same effects expressed as costs rather than limits are `cost.temporal_scope.cumulative.{investment,operation}`, cross-referenced both ways.
  - **`reliability` stays a group, but only for limits that engage a failure state.** Its members are not distinguished by their form in time, so they cannot be cut by `temporal_scope`; what they share is that each engages a failure or contingency state the taxonomy's dimensions do not carry, and each introduces a quantity that exists nowhere else in the model — a per-asset reserve provision co-optimised with dispatch, a probability of shortfall, a post-contingency dispatch. That is a tighter rationale than "the quantity held against an adequacy or security target", and it costs the group a member.
  - **`margin_requirement` is dissolved.** A planning reserve margin is `Σ de-rated capacity ≥ margin × peak demand`: a lower bound on *accumulated installed capacity*, sized by an input parameter, with no failure state in the constraint itself. So `margin_requirement.capacity` → `constraints.temporal_scope.cumulative.investment.capacity_target`, which is widened to say that capacity may be counted at a per-asset de-rating or capacity-credit factor rather than at nameplate, and is recorded across a fleet or system via `constraints.breadth.combined.investment`. It is *not* a `pointwise` investment limit: `pointwise.investment.size_bounds` bounds capacity *added within* a period, which is a different quantity. What the move does not capture is a requirement whose right-hand side is derived endogenously (from peak demand, or from the largest credible contingency); that is the general "dynamic constraint RHS" gap, tracked separately, not a reason for the leaf to survive.
  - **`constraints.reliability.margin_requirement.operating_reserve` → `constraints.reliability.operating_reserve`, cut by provision source rather than by market product.** The previous `spinning` / `non_spinning` / `regulation` / `flexible_ramping` / `inertia` split records market vocabulary, not tool capability: PLEXOS implements all of it with a single generic `Reserve` class whose `Type` attribute takes eight values (raise, lower, regulation, regulation raise/lower, replacement, operational, inertia), with flexible ramping expressed as a reserve carrying a `Max Response` cap rather than as a type at all; PyPSA has no reserve attribute on any component. Those five leaves therefore near-perfectly co-vary. What does vary is what provision can be drawn from — PLEXOS's own list is "spare capacity on running generators, interruptible load, synchronous condenser plant, plant on stand-by", with inertia read off a separate `Generator.InertiaConstant` and explicitly not energy-limited. Hence `online_headroom` (spare capability on running assets, bounded by the flow-to-capacity gap and how fast it can be closed), `standby_capability` (offline but startable within a response time; requires unit commitment) and `inertia` (stored rotational energy rather than power headroom). Direction and response time are parameterisations within these, not separate features.
  - `constraints.scope.total.operation.emissions_budget` → `constraints.temporal_scope.cumulative.operation.impact_budget`, widened from "cumulative production of a non-carrier byproduct" to production *or consumption* of any non-carrier quantity, so that water abstraction, land take and material use are covered alongside emissions. Both tools surveyed treat the impact type as a user-supplied parameter rather than as distinct features, so this stays one leaf rather than mirroring the `emissions` / `resource_use` / `socioeconomic` split of `postprocessing.metrics.impact_assessment`, where the post-hoc calculations genuinely do differ.
  - `constraints.temporal_scope.boundary_conditions.operation` is widened from initial/end-state conditions to also cover limits on how far those states may move between periods, which is how changeover between investment periods is managed. Conditions at the *spatial* edge of the system are deliberately not leaves here: the flows are `processes.boundary_exchange`, limits on them are the ordinary temporal leaves applied to that exchange, and mitigating the distortion the edge creates is `edge_effects`.
- **Named constraints and costs become features in their own right (#127).** The taxonomy previously named concrete quantities in `postprocessing.metrics` but left `constraints` and `cost` abstract, with the concrete capabilities buried in `e.g.` hints. Those hints are promoted to leaves, so a list can record *which* named limit or cost a tool supports rather than only that it supports the abstract class. The ten leaves enumerated below become branches and the taxonomy grows from 190 to 222 leaves. Because a branch may not sit alongside the `investment` / `operation` axis members, these nest *below* that axis, taking the deepest paths from four segments to five.
  - `cost.functional_form.nonlinear.operation` → `flow_dependent` / `bid_bands` (it previously named only bid increments, omitting heat-rate and fuel-offtake curves); `cost.annuitisation` → `discounting` / `fiscal_treatment`. `cost.functional_form.fixed_charge.investment` stays a leaf: a lump sum charged per unit built and one charged once for a group of assets differ in *what the cost attaches to*, not in its form, and the group case is already recorded by `cost.breadth.assets.investment`.
  - `cost.temporal_scope.sequential` (was `inter_temporal`) is widened from "the magnitude of change in a decision variable" to any change in one, so that lump-sum transition costs belong here alongside magnitude-proportional ones; `cost.temporal_scope.sequential.operation` → `start_up` / `shut_down` / `ramping` / `start_state_dependent`. Start-up and shut-down costs are a lump sum on a *transition between* timesteps, so they belong here rather than under `pointwise`.
  - **`cost.functional_form.fixed_charge.operation` is redefined** as a consequence: having given up start-up costs, it now covers what is genuinely a lump sum irrespective of magnitude — cost incurred for each timestep an asset is committed, regardless of its flow (no-load / stand-by cost). Existing `y`/`n` answers for this leaf should be re-checked rather than carried across on migration.
  - `constraints.temporal_scope.sequential.operation` → `ramping` / `start_shut_trajectory` / `commitment_duration` / `start_consumption`; `…pointwise.operation` → `availability_derating` / `minimum_stable_level` / `forced_offline` / `forced_online`; `…sequential.investment` → `build_rate` / `retirement` / `availability_window`; `…pointwise.investment` → `size_bounds` / `discrete_increments` / `unit_purchase`.
  - `constraints.temporal_scope.cumulative.operation` → `flow_volume` / `impact_budget` / `event_count` / `state_duration`, widening it beyond carrier in-/out-flow to cover non-carrier quantities; `…cumulative.investment` → `capacity_target` / `expansion_budget` / `event_count`.
  - `constraints.reliability.operating_reserve` → `online_headroom` / `standby_capability` / `inertia`, distinguished by what provision can be drawn from rather than by any one market's product names (see above).
- **`model_definition`** is new, holding `multi_period`, `dimension_groups`, `component_templating`, `configurable_dimensions`, and `extensible_dimensions` — how the model's parameter space can be shaped, grouped, or reused, as distinct from what an asset does.
- **`math`** holds properties of the optimisation problem itself: `formulation_transparency`, `problem_file_export`, `dual_extraction`, `piecewise_formulation`, `user_defined_math`, `soft_constraints`.
- **`interface`** is organised by access mode (`gui`, `api`, `cli`), each sliced by workflow stage (`build` / `run` / `analyse`), plus `remote_execution`, `solver_configuration`, `analysis_templates`, and `visualisation` (`charts`, `network_maps`).
- **`io`** replaces the I/O half of `interface__input` / `interface__output`: `plain_text`, `binary`, `database`, `remote_storage`, `lazy_loading`, and `standardised` (community conventions and ontologies, including network-data formats such as PSSE RAW, matpower and CIM), each sliced `input` / `output`.
- **`tractability`** gathers all simplification and solution-strategy features into `dimension_reduction`, `variable_fidelity` and `reformulation`, replacing `time__resolution__simplification`, `spatial__resolution__simplification` and the solver-side half of `optimisation_problem`.
  - `dimension_reduction` is sliced **method over dimension** rather than dimension over method, so that methods recurring across dimensions are stated once and a dimension beyond time/space/assets can be reduced (#125). Its members are `adjacency_aggregation` (merge neighbours, ordering preserved), `similarity_aggregation` (group by likeness, possibly non-contiguous), `equivalencing` (discard internals, preserve boundary behaviour), `filtering` (remove members outright), and `non_contiguity_handling`; each names only the dimensions it can act on, drawn from `temporal` / `spatial` / `assets` / `scenarios`. Old → new: `…temporal.resampling` → `…adjacency_aggregation.temporal`; `…temporal.typical_periods` and `…temporal.load_duration_curves` → `…similarity_aggregation.temporal`; `…spatial.clustering` → `…adjacency_aggregation.spatial` or `…similarity_aggregation.spatial` depending on whether the tool clusters on adjacency or on likeness; `…assets.clustering` → `…similarity_aggregation.assets`; `…spatial.network_reduction` → `…equivalencing.spatial`; `…assets.black_boxing` → `…equivalencing.assets`; `…assets.component_removal` → `…filtering.assets`; `…temporal.dimension_non_contiguity` → `…non_contiguity_handling.temporal`.
  - `variable_fidelity` is promoted from a leaf of `reformulation` to a branch of `tractability`, because differing fidelity applies to resolution as much as to formulation (#124): `tractability.reformulation.variable_fidelity` → `tractability.variable_fidelity.formulation`, alongside a new `tractability.variable_fidelity.resolution`. `resolution` is sliced by the dimension whose resolution varies (`temporal` / `spatial` / `assets` / `scenarios`), with the dimension it varies across given by example — e.g. `…resolution.temporal` covers hourly in-region and daily elsewhere, `…resolution.spatial` covers nodal near-term and zonal beyond. This is the counterpart to `dimension_reduction`, which reduces a dimension uniformly across the rest of the problem.
  - `reformulation.convex_relaxation` and `reformulation.function_conversion` are grouped under a new `reformulation.nonlinear_handling` branch (#123). They are kept distinct: one relaxes a non-convexity in the model's own formulation, the other converts a user-supplied function into valid model inputs.
  - `numeric_scaling` moves from `preprocessing` to `tractability.reformulation`, being a treatment of the built problem rather than of the input data.
- **`orchestration`** covers how many model runs happen and how they relate: `coupled_models`, `scenario_runs`, `sampled_runs`. `coupled_models` becomes a branch grouped by **why** the runs are coupled rather than by what kind of model is coupled (#122), since the previous three siblings were all couplings distinguished only incidentally: `rolling_horizon` → `coupled_models.limited_foresight` (now sliced `investment` / `operation`, absorbing `pathway.myopic_foresight`); `coupled_models` → `coupled_models.market_sequence`; `simulation_optimisation` → `coupled_models.convergence_iteration` (broadened to any convergence loop, e.g. iterating on line reactances).
- **`uncertainty`** is rescoped to stochastic decision methods (`two_stage_stochastic`, `multi_stage_stochastic`, `risk_aversion`, `near_optimal`, `robust_optimisation`), with the deterministic reliability constraints it used to hold moved to `constraints.reliability`.
- **`actors`** replaces `competition`, adding `equilibrium` (computed: Cournot-Nash, Bertrand) and `heuristic_markup` (rule/index-based strategic markups) to `portfolio` and `distributed_objectives`.
- **`pathway`** is dissolved (#128). Myopic foresight is a coupling of sequential runs, so `pathway.myopic_foresight.{investment,operation}` → `orchestration.coupled_models.limited_foresight.{investment,operation}`. Perfect foresight is not simply the baseline — a single snapshot is — so the ability to optimise several periods simultaneously survives as `model_definition.multi_period.{investment,operation}`. `time__foresight` and `time__horizon` are therefore both gone, and horizon length remains a non-feature.
- **`objective`** is new: `multi_objective_weighted`, `multi_objective_pareto`, `quadratic`, and `tie_breaking` — resolving degenerate solutions by a documented rule, e.g. small penalty coefficients on otherwise zero-cost decision variables (#126). It sits here rather than under `tractability`, which is explicitly about trading exactness for speed.
- **`preprocessing`** adds `resource_conversion` (physical response models turning weather/resource data into availability or demand profiles), `scenario_generation`, `input_validation`, and `model_catalogue`, with `forecasting` rescoped to scaling and reshaping existing profiles.
- **`postprocessing`** splits into `metrics` — quantities derived from outputs, grouped by what is being reported (`impact_assessment`, `operational`, `financial` including `levelised_cost` / `marginal_price` / `price_formation` / `contract_settlement`, `network_transfer_metrics`, and `probabilistic_reliability_assessment` with `loss_of_load` / `unserved_energy` / `capacity_credit`) — and `transformation`, which reshapes outputs without deriving new quantities (`aggregation`, `disaggregation`, `scenario_comparison`) (#129).
- **`traceability`** is new, consolidating debugging and provenance concerns: `run_logs`, `infeasibility_diagnosis`, `intermediate_access`, and a `metadata` branch (`provenance`, `units`, `propagation`).

### Removed

- The `baseline` field on every feature. Members are now flat `key: "description"` entries; whether a capability is fundamental or advanced is a property of the tool landscape, not of the taxonomy.
- `time__horizon`: horizon length is no longer a feature, being absorbed into `pathway` and `orchestration.rolling_horizon` (#87).
- `asset__resolution`: `units` / `grouped` are the two sides of `decisions.investment`, while aggregating physical assets is `tractability.dimension_reduction.similarity_aggregation.assets` and `mixed` generalises to `tractability.variable_fidelity`.
- `edge_effects.spatial`, subsumed by `processes.boundary_exchange`.
- `resource_adequacy` and `optimisation_problem` as groups; their members are distributed across `constraints.reliability`, `postprocessing`, `orchestration`, `tractability`, `uncertainty`, `interface`, and `math` according to what they describe rather than what they were used for.
- Features that stated a baseline capability every tool has, rather than a distinguishing one: `system__carriers.decoupled` (single-carrier modelling), `transmission__opf.transport` and `transmission__limits.gtc` (both folded into `processes.spatial_transfer`), `asset__operating_characteristics.static_non_dimensional` / `.static_dimensional` (replaced by `model_definition.configurable_dimensions` / `.extensible_dimensions`, #112), `asset__operating_characteristics.linear` (a linear parameter-to-variable relationship is the LP baseline), and `asset__cost__investment.linear` / `asset__cost__operation.linear` (linear EUR/MW capital and EUR/MWh operating costs are the baseline cost representation).

## 0.2.0 (2026-08-26)

### Removed

- Removed "a.k.a." in feature descriptions in preparation for a separate `also_known_as` option.
- Detailed power-system simulation groups (`transmission__network`, `power_flow__controls`, `power_flow__contingency_analysis`, `power_flow__sensitivity_analysis`, `power_flow__dynamic_simulations`), which are out of scope for a planning-tool feature list.

### Changed

- Updated `asset__chaining.stockpiling` feature description to better distinguish it from general storage asset representation (#31).
- Moved `asset__candidates.endogenous` and `asset__candidates.exogenous` to `asset__capacity_representation` and expanded `endogenous` to `continuous_capacity`, `integer_investment_exogenous_capacity`, and `integer_investment_continuous_capacity` (#54).
- Moved `asset__capacity_representation` items into a new `asset__resolution` group to clarify their purpose, as features related to asset detail (#54).
- Default feature value to `null` (i.e., unknown) rather than `n` (i.e. not present).
- Renamed `ldc` -> `load_duration_curve`, `fluid/gas_distribution` -> `fluid_or_gas_distribution`, `fcf` -> `future_cost_function`.
- Simplified `asset__operating_constraints` by grouping features that span the time dimension (ramping, run up, etc.) into a `inter_temporal` feature.
- generalised `asset__operating_constraints.load_rate` into a `asset__operating_constraints.operating` feature for unit-commitment constraints.

### Added

- Added `baseline` for every feature value to differentiate between fundamental and advance feature.
- Pull request template checklist item, to remind contributors to update the changelog.
- README preamble.
- Use-cases and a specific template and schema for them (#16), with lists for bidding zone review, integrated resource planning, network development planning, policy target setting, and portfolio planning.
